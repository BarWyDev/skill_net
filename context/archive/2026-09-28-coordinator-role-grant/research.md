# Research: Coordinator role grant (S-02)

Written by hand because `/10x-research` isn't installed in this session. It is input for `/10x-plan coordinator-role-grant`.

## Goal (from the roadmap)

The operator can grant a registered user the coordinator role. A coordinator sees a coordinator-only area that residents and anonymous visitors cannot open. PRD FR-017: "Operator can assign the coordinator role", must-have. PRD role matrix: the coordinator is a "regular account; role assigned manually by the operator", and the operator is the product owner. The MVP does no institutional vetting.

S-03's security-definer ranking RPC is the first real consumer. The role check therefore has to work **inside Postgres**, not only in the middleware.

## Options for storing the role

### A. `public.user_roles` table plus an `is_coordinator()` SQL helper (recommended)

- Table: `user_id uuid pk references auth.users on delete cascade`, `role text check (role in ('coordinator'))`, `granted_at timestamptz default now()`, `granted_by text` (a free-text note naming the operator, since the operator has no app account role).
- `public.is_coordinator()` returns boolean. It is `stable`, `security definer`, `set search_path = ''`, and checks `exists (… where user_id = auth.uid() and role = 'coordinator')`. S-03's RPC calls it first and raises `not_coordinator` when it's false.
- RLS: the owner can read their own row. There are **no** insert, update or delete policies for `anon` or `authenticated`, so nobody can promote themselves through PostgREST. The operator grants the role through the Supabase SQL editor as `postgres`, which bypasses RLS.
- Revocation takes effect on the next request, with no token-staleness window.
- Cost: one extra DB round trip on each coordinator-area request. Only coordinator routes pay it, not every request. It fits well within the Free plan's 50-subrequest limit.

### B. `auth.users.raw_app_meta_data.role`, read from the JWT

- Only a service role or the SQL editor can write it, so it's safe from self-promotion, and it reaches the JWT for free.
- A granted or revoked role doesn't take effect until the token refreshes, which can take **up to 1 h** (`jwt_expiry = 3600`). Revoking access to personal data an hour late is poor for this product.
- Postgres can read it through `auth.jwt() -> 'app_metadata'`, but it would be the only piece of domain state kept outside `public`.

### C. Custom access token hook plus a roles table (Supabase's documented RBAC pattern)

- Keeps the claim in the JWT, but needs a hook enabled in `config.toml` **and** in the hosted dashboard. That hosted step is a human-only production config change.
- It has the same 1 h staleness as B. The extra machinery is worth it only once there are many roles or permissions, and v1 has exactly one elevated role.

**Recommendation: A.** It's the smallest option, revocation is immediate, it matches the existing migration style, and it gives S-03 a single DB-side gate. The operator role stays out of the app (the product owner uses Studio). FR-018, the in-product operator tooling, is parked, so the MVP needs no operator UI.

## How the operator grants the role

The options, in order of simplicity:

1. **A documented SQL snippet** run in the Supabase SQL editor, which inserts by email: `insert into public.user_roles (user_id, role, granted_by) select id, 'coordinator', '<operator>' from auth.users where email = '…'`. Revoking is a `delete`.
2. **A `grant_coordinator(p_email text, p_note text)` function**, with execute revoked from `public`, `anon` and `authenticated` so only `postgres` and `service_role` can call it. It gives clearer errors (unknown email, already granted), and the pgTAP tests can call it too. Slightly more code.
3. An admin screen. This needs an operator role in the app and is out of scope (see FR-018 parked).

Option 2 is the better choice if the plan wants the grant path itself under test. Otherwise option 1 plus a runbook entry is enough.

**Audit.** A grant gives access to other people's personal data once S-03 ships. `granted_at` and `granted_by` on the row record grants, but a `delete` erases the history of revokes. If the plan wants an append-only trail, add a `role_grants_log` table written by the function (or a trigger). S-05 and S-09 introduce audit tables later, so an audit table here could share their shape. That is a question for the plan to settle.

## The coordinator area

- A new route, in Polish, following `/profil`: `/koordynator` (for example `src/pages/koordynator/index.astro`). For now it's a placeholder panel ("Panel koordynatora", with crisis activation arriving in S-03).
- **Guard in two layers:**
  1. The middleware keeps redirecting anonymous users to sign-in (add `/koordynator` to `PROTECTED_ROUTES`, which is the Open Question 6 default).
  2. For signed-in users, the page (or a middleware branch limited to `/koordynator`) calls `is_coordinator()`. When it's false, the answer is **403** with a Polish "Brak dostępu" page. The alternative is a redirect to `/profil`: a 403 is clearer and testable, while a redirect hides that the area exists. Whichever the plan picks, the smoke step must assert it.
- **Fail closed.** If the RPC errors (the migration hasn't been pushed yet, or Supabase is down), deny access. Never treat an error as "is a coordinator".
- **Cache.** Coordinator responses must use `Cache-Control: private, no-store`. This is a lesson from `context/foundation/lessons.md`: never use `public` on routes that pass through the auth middleware.
- **Nav.** Show a "Koordynator" link in `Topbar.astro` only to coordinators. That needs the role flag at render time. Either call `is_coordinator()` in the middleware for every signed-in request (one extra round trip everywhere) or skip the link and give coordinators the URL. The plan should choose; showing the link only on `/dashboard` is a cheap middle ground.
- Optionally expose it as `Astro.locals.isCoordinator`, typed in `src/env.d.ts`, if the middleware computes it.

## Tests

- **pgTAP** (new `supabase/tests/coordinator_role_test.sql`):
  - A resident gets `is_coordinator() = false`, and a granted user gets `true`.
  - An `authenticated` user cannot insert, update or delete `user_roles`, including for themselves (proves there's no self-promotion).
  - A user reads only their own role row. Anon reads nothing.
  - If option 2 is chosen, `grant_coordinator` isn't executable by `authenticated`.
  - Deleting the user from `auth.users` cascades and removes the role.
- **Smoke** (readonly-safe):
  - Anonymous `GET /koordynator` gives 302 to `/auth/signin`.
  - In the write steps, a freshly signed-up resident gets `GET /koordynator` as 403 (or the redirect chosen).
  - The positive path (a coordinator sees the panel) can't be smoked without a service key. pgTAP plus a manual check covers it.

## Deploy ordering

- The migration is purely additive (a new table and function). Push it with `npx supabase db push` **before** merging, as S-01 did. If the code ships first, `is_coordinator()` is missing, the RPC errors, and the fail-closed rule denies everyone. That is safe, but it looks broken to the first coordinator.
- Granting the first real coordinator on production is a human step in the SQL editor after the push. It is a production data change.

## Open decisions for the plan

1. Where the role is stored: A, B or C. The recommendation is A.
2. The grant path: a SQL snippet or a `grant_coordinator()` function.
3. Whether grants and revokes need an append-only audit table now, or whether the columns on `user_roles` are enough until S-05/S-09.
4. What a signed-in non-coordinator gets: 403 or a redirect.
5. The route name: `/koordynator` or another Polish slug.
6. Nav visibility: a role lookup on every request, only on `/dashboard`, or no link.
7. Whether to fix Open Question 6 formally. Anonymous visitor → sign-in redirect is the current default, and the change can simply record it.
